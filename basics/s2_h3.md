# Geospatial Indexes: S2 and H3

> **TL;DR** — **S2** (Google) and **H3** (Uber) are hierarchical **spatial cell systems** that fix geohash's weaknesses. **S2** projects the sphere onto a cube, orders cells along a
> **Hilbert curve**, and gives each cell a 64-bit id so that nearby cells have nearby ids (efficient range scans) and any region can be covered by a small set of cells (**region covering**).
> **H3** tiles the globe with **hexagons** (16 resolutions): every neighbor is the same distance away, which is ideal for **proximity, smoothing and aggregation** (surge pricing, heatmaps).
> Use S2 for indexing/range queries and covering polygons; H3 for analytics and neighbor-based logic. Basics: [Geohash & Quadtree](geohash_quadtree.md); also [Uber](../problems/uber.md), [Google Maps](../problems/google_maps.md).

## Why not just geohash?
Geohash cells are rectangles on a lat/lng grid: they **distort near the poles**, neighbors are at different distances (edge vs corner), and adjacent cells may not share prefixes. Better systems
use **equal-area-ish cells** and **space-filling curves with better locality**.

## S2 geometry
- Maps the Earth to a **cube**, subdivides each face as a quadtree (levels 0-30; level 30 ≈ 1 cm²), and numbers cells by a **Hilbert curve** so spatially near cells tend to have near ids.
- **Cell id** is a 64-bit integer (face + position along curve + level). A parent's id range **contains** its children's ids, so *"all points inside cell C"* is a **single range scan** over a sorted index.
- **Region covering**: approximate any shape (circle, polygon) with a few cells at mixed levels (`S2RegionCoverer`) → query those ranges → exact-filter. Great for geofences and radius search.
- Used by Google Maps, Bigtable-based location stores, MongoDB `2dsphere` indexes, Foursquare, CockroachDB/PostGIS integrations.
- **Pros**: precise, hierarchical, locality-preserving ids, fast range scans, handles polygons/covering. **Cons**: more complex than geohash; cells are squares on a cube (neighbors still differ between edge/corner).

## H3 (hexagonal hierarchical index)
- Icosahedron projection with **hexagonal cells** at 16 resolutions (res 0 ≈ continental, res 9 ≈ 0.1 km², res 15 ≈ 1 m²); each hex has **6 equidistant neighbors** (plus 12 pentagons at the icosahedron vertices).
- Operations: `latLngToCell`, `gridDisk(cell, k)` (k-ring neighbors), `cellToParent/Children`, `polygonToCells`.
- **Why hexagons**: uniform adjacency simplifies **smoothing, spreading, and radius** logic (no corner-neighbor distortion); ideal for **demand/supply balancing**, surge pricing, ETA heatmaps, spatial aggregation.
- Hierarchy is approximate (children aren't perfectly nested), so prefix/range tricks are weaker than S2; H3 ids are typically indexed as plain keys (cell id equality / `IN (neighbors)`).
- **Pros**: uniform neighbors, great for analytics, simple API in many languages. **Cons**: not perfectly nested, pentagons, less natural for polygon range scans.

## Comparison
| | Geohash | Quadtree | S2 | H3 |
|---|---|---|---|---|
| Cell shape | Rectangles | Squares (adaptive) | Squares on cube faces | Hexagons (+12 pentagons) |
| Locality | Z-order (prefix) | Tree | Hilbert curve | Hierarchical cell ids |
| Neighbor distance | Non-uniform | Non-uniform | Non-uniform | **Uniform (6 neighbors)** |
| Range scan on id | Prefix scan | n/a (tree) | **Contiguous id ranges** | Equality / IN list |
| Polygon covering | Awkward | Possible | **Excellent** | Good (`polygonToCells`) |
| Best for | Simple KV proximity | Dense in-memory k-NN | Indexing, geofences, DB range queries | Aggregation, surge, heatmaps |

## Design usage
- **Ride-hailing (Uber)**: H3 cells for supply/demand per region, surge pricing, dispatch search via `gridDisk` rings; keep driver locations in an in-memory/Redis index keyed by cell ([Uber](../problems/uber.md)).
- **Geofencing / "is this point inside any of 1M polygons"**: S2 coverings of polygons stored as cell-id ranges; point → cell id → range lookup → exact check.
- **Maps/tiles/routing graph partitioning**: S2 cells as shard keys giving locality ([Google Maps](../problems/google_maps.md)).
- **Analytics**: aggregate events by H3 cell at a chosen resolution; roll up to parents; join across datasets on cell id.

## Pitfalls
- Picking a resolution/level that doesn't match the radius (too many/few cells); ignoring pentagons/face boundaries; assuming H3 children nest exactly; forgetting exact-distance post-filtering.
- Cells as shard keys → hot cells in cities; use finer levels or composite keys ([Hot keys](hot_keys.md)).

## Interview follow-ups
- *"Why use S2/H3 over geohash?"* Uniform shapes, better locality, region covering (S2), uniform neighbors (H3).
- *"How do you search within 2 km?"* Choose a resolution whose cell edge ≈ radius, compute the cell + k-ring (H3) or a covering (S2), fetch candidates, filter by exact distance.
- *"How do you index a polygon?"* Cover it with S2 cells; store cell ids; query by point's cell id and ancestors.
